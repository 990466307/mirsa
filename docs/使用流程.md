# 使用流程

先按 [README](../README.md) 准备编译环境。完整示例见 [examples/query_annotations.rs](../examples/query_annotations.rs)：

```bash
cargo run --locked --features z3 --example query_annotations
```

源码文件中的查询全部通过 `#[mirsa::check(...)]`、`#[mirsa::facts(...)]` 声明；源码 API 和 CLI 不再接受外部 DSL、变量别名表或 `// mirsa: 名字` 位置标注。

```rust
use mirsa::Mirsa;

fn main() -> Result<(), mirsa::Error> {
    for query in Mirsa::from_file("/path/to/your.rs").analyze_annotations()? {
        println!("{}:{}:{} {}", query.file, query.line, query.column, query.query);
        println!("{}", query.report);
    }
    Ok(())
}
```

返回 `Result<Vec<AnnotationReport>, mirsa::Error>`。每条属性有独立的位置、查询表达式和结果；没有启用的查询属性时返回空列表。

```rust
pub struct AnnotationReport {
    pub file: String,
    pub line: usize,
    pub column: usize,
    pub query: String,
    pub report: Report,
}
pub struct Report { pub output: Output }
pub enum Output { Check(CheckReport), Facts(FactOutput) }
```

性质结果读取 `query.report.output` 中的 `CheckReport.result`、`status`、`definite_violation` 和 `unreachable`。状态为 `proved`、`violated`、`maybe_violated` 或 `unreachable`。`result=false` 不能单独判漏洞；Z3 超时或未完成判定时采用抽象分析结论并在逐路径 `notes` 中说明。编译、绑定、表达式错误或不支持的查询返回 `Err`，诊断位置相对于属性中的表达式。

`facts` 返回 `FactOutput.paths`，每条路径有 `path_id`、`merged`、`abstract_info` 和 `symbolic_info`。`merged=true` 表示多条执行的抽象合并，不能把不同取值范围拼成一条真实执行。

## 直接使用源码属性

可以把查询写在待分析语句或表达式上，不再单独提供 DSL或位置名：

```rust
pub fn example() -> u8 {
    let table = [10u8, 20, 30];
    let index = 5usize;

    #[mirsa::check(index < len(table))]
    #[mirsa::facts(index)]
    #[mirsa::facts(table)]
    let value = unsafe { *table.get_unchecked(index) };
    value
}
```

属性查询检查被标注语句**执行前**的状态。同一位置可以叠加多个属性，每个属性独立返回结论和逐路径证据。作用域、同名变量遮蔽、`cfg` 筛选按 rustc 实际解析的源码处理。当前支持语句和表达式属性，不支持函数级查询属性或宏生成的位置。

MIRSA driver 自动注册 `mirsa` 工具命名空间，直接识别 `#[mirsa::check(...)]` 和 `#[mirsa::facts(...)]`，不需要过程宏依赖。带这些属性的源码通过 MIRSA 运行。

将上面的源码保存到自己的 `.rs` 文件后，用实际路径替换下文的 `/path/to/your.rs`。Rust 接口一次执行文件中的所有属性查询：

```rust
let reports = mirsa::Mirsa::from_file("/path/to/your.rs").analyze_annotations()?;
for query in reports {
    println!("{}:{}:{} {}", query.file, query.line, query.column, query.query);
    println!("{}", query.report);
}
```

每个 `AnnotationReport` 包含 `file`、`line`、`column`（从 1 开始）、`query` 和原有的 `report`。证据仍位于 `report.output` 中每条路径的 `evidence.expressions`。

也可以运行 CLI，输出 `{"status":"ok","reports":[...]}`：

```bash
cargo run --locked --features cli,z3 --bin mirsa-query -- /path/to/your.rs
```

JSON worker 只接受带属性的源码或文件，例如 `{"file":"/path/to/your.rs"}` 或 `{"source":"带属性的完整源码"}`，可附 `rustc_args`。外部 `dsl`、`bindings` 参数会被拒绝。

### 不使用 dollar 时如何区分名字

- `len(table)`：调用位置的 `len` 是 builtin，参数 `table` 是源码变量。
- 单独的 `len`：源码变量，即使它与 builtin 同名。
- `table.field`：`table` 是变量，`field` 是字段名。
- `unknown(table)`：未知调用会报告 DSL 错误，不会猜成 builtin 或执行用户函数。

例如函数参数名为 `len` 时，`#[mirsa::check(len < len(table))]` 仍明确表示“变量 len 小于 table 的长度”。已有 MIR 的内部工具接口仍使用显式的 `Bindings`；源码入口不需要 dollar 符号。

## 工具开发：已有 MIR 的接口

以下是供 RPL 等工具使用的底层接口，不是源码文件查询入口。调用方已持有 MIR 值与位置时，可直接绑定这些编译器对象。

在工具的 rustc 回调中，已有 `tcx: TyCtxt<'tcx>`、`body: &Body<'tcx>`、匹配出的 `index_place` / `slice_place: Place<'tcx>` 和目标 `location: Location` 时：

```rust
use mirsa::query::Bindings;

let bindings = Bindings::new()
    .value("i", index_place)
    .value("s", slice_place)
    .location("access", location);
let report = Mirsa::from_mir(tcx, body)
    .query("$i < len($s) at 'access", &bindings)?;
```

两种入口使用同一套分析和结果类型。

## 逐路径事实与判定证据

本节描述当前工作区在 0.4.0 基础上增加的功能，远端 `v0.4.0` 尚不包含这些扩展。使用这些返回字段时，请依赖当前工作区源码（例如上面的 `path` 依赖）。

`facts($x)` 不再合并各路径的事实。按 `output.paths` 遍历，每个 `PathFacts` 单独保留该路径上的范围和符号关系。不可达位置返回 `unreachable=true, paths=[]`。这是输出接口变更：原来的 `facts.abstract_info` 改为 `facts.paths[i].abstract_info`，符号信息同理。路径编号只在本次分析结果中有意义，不是源码路径或执行轨迹。

优先读取 `check.paths[i].evidence.expressions`，这是按表达式展示的证据：

```json
{
  "kind": "abstract",
  "facts": ["index = 5", "len(table) = 3"],
  "goal": "(index < len(table))",
  "result": false
}
```

抽象推理列出参与求值的表达式及其取值，不展开重复布尔包装和常量节点。SMT 则返回 `kind="smt"`、`variables`、`assumptions`、`goal`、`negative`、`positive`；`assumptions` 与原始输入公式一一对应，保留顺序、重复项和恒真式。这是提交给求解器的全部前提，不是最小证明集合。变量名使用查询绑定名，未命名的 MIR 临时变量保留 `_3` 等名称。数值的 `u64` / `i32` 后缀和 `bits::<类型>(...)` 表示机器整数类型及其位宽运算；`math(...)` 表示数学整数。底层编码仍以 `smt.problem` 和 SMT-LIB 为准。

`println!("{report}")` 默认展示该表达式视图。JSON 中仍保留下面的完整记录，供需要时查看。

性质查询返回 `CheckReport`，优先通过 `status` 读取四种结论；`result`（布尔值）或 `verdict`（T/F）保留是否已证明的信息。每个 `CheckReport.paths[i]` 包含该路径的 `status`、`source`、`evidence` 和附加说明 `notes`；底层 `AnalysisView::check()` 返回的 `Proof` 使用同样的逐路径结构：

- `abstract_evaluation`：递归求值树，每个节点含 `expression`、`rule`、`value`、`premises`。例如比较节点的两个前提分别记录 `$i ∈ [0,7]` 和 `8 ∈ [8,8]`，比较节点结果为 `Bool(true)`；查询 `$i >= 8` 则为 `Bool(false)`，对应确定违反。可能为真也可能为假的布尔值记录为 `Bool(null)`。抽象分析预算不足而未完成时，查询返回错误。
- `context`：该路径中与目标相关的已存储符号事实，用于理解求值上下文；它不是最小前提集合，也不表示每条事实都参与了推导。
- `smt`：仅在补充求解完成并采用其结果时存在。`problem.assumptions` 是前提 A，`problem.property` 是性质 P，均为保留位宽、符号性及运算的结构化公式。`bindings` 将标量变量编号映射到程序表达式。Z3 超时或未完成判定时，此字段为空，`source=Abstract`，表达式证据也使用抽象分析视图，附加情况在路径的 `notes` 中说明。

`checks.negative` 是 `A ∧ ¬P` 的实际求解结果；`checks.positive` 是 `A ∧ P` 的实际结果，尚未检查时为空。结果组合为：

| negative | positive | 含义 |
|---|---|---|
| unsat | sat | 成立 |
| sat | unsat | 确定违反 |
| sat | sat | `maybe_violated`，模型允许性质成立或不成立 |
| unsat | unsat | 不可达 |
| unknown | 任意或未检查 | 不采用该次求解结果，使用抽象分析结论和证据，并附加说明 |

`checks.assumptions_smtlib` 保留后端断言与符号声明（包括引入目标符号的恒真式），`checks.goal_smtlib` 保留实际目标。在前者后附加 `(assert (not <goal>))` 和 `(check-sat)` 可复查反目标；在另一份独立脚本中附加 `(assert <goal>)` 和 `(check-sat)` 可复查正目标。此证据是公式和判定记录，不是独立形式证明证书或 unsat core。

`candidate` 若存在，是已完成求解中反目标可满足时的抽象候选模型，不保证对应真实执行。通过 `status` 区分确定违反、可能违反和不可达，不能单凭 `F` 认定程序有错。
